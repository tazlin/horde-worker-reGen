# Run a text worker

A *scribe* serves text-generation jobs. The text itself is generated by a separate program, the text
backend (koboldcpp today), which the worker talks to over HTTP. The worker can download, launch and
supervise that program for you, or attach to one you already run.

Text generation is in beta. A text-only worker, and text on its own card of a multi-GPU host, are the
supported shapes. Text and image generation sharing one card works but is experimental: nothing yet stops
the two from competing for VRAM beyond the headroom you leave yourself.

A scribe is a separate horde worker from your dreamer or alchemist. It has its own name, its own kudos
line on the dashboard, and appears as a text worker on the horde.

## Let the worker run the backend

1. Open `bridgeData.yaml` and turn the role on with a name that is unique horde-wide and differs from your
   other worker names:

   ```yaml
   scribe: true
   scribe_name: "My Unique Scribe"
   ```

   For a text-only worker also set `dreamer: false`. A text-only worker starts no image processes at all.

2. Choose a model. Name one from the catalogue and the worker fetches it on first launch, resuming an
   interrupted download and checking the file against its recorded digest:

   ```yaml
   text_model: "meta-llama/Meta-Llama-3.1-8B-Instruct-Q4_K_M"
   ```

   | Catalogue name | Download | VRAM used | Measured speed |
   | -------------- | -------- | --------- | -------------- |
   | `meta-llama/Llama-3.2-3B-Instruct-Q4_K_M` | 2.0 GB | 2.9 GB at 4k context | about 190 tok/s |
   | `meta-llama/Meta-Llama-3.1-8B-Instruct-Q4_K_M` | 4.9 GB | 6.0 GB at 8k context | about 106 tok/s |
   | `mistralai/Mistral-Nemo-Instruct-2407-Q4_K_M` | 7.5 GB | 8.6 GB at 8k context | about 73 tok/s |

   The figures were measured on a 16 GB RTX 4070 Ti SUPER with the whole model on the card. Files are kept
   in `text_models_dir`, which defaults to a `text_models` folder under your model cache.

   To serve a GGUF of your own, give its path instead. It is used where it sits and never copied:

   ```yaml
   text_model: "D:/models/My-Model-Q5_K_M.gguf"
   text_model_name: "author/My-Model-Q5_K_M"
   ```

   `text_model_name` is the name the horde knows the model by, without a backend prefix; the worker adds
   the prefix. Leave it unset and the file's stem is advertised.

3. Set what you offer. `max_context_length` is also the context the backend is launched with, and VRAM use
   grows with it:

   ```yaml
   max_length: 512
   max_context_length: 8192
   ```

4. Start the worker. On first launch it downloads a pinned koboldcpp release (about 600 MB for the NVIDIA
   build) into `bin/` and the model file if it is a catalogued one. The dashboard shows the backend as a
   row of its own while that happens, then "warming up", then ready. The backend's own output is in
   `logs/text_backend.log`.

### Which card, and which compute path

On a multi-GPU host, name the card text should have. That card is removed from image generation, so the two
never compete for it:

```yaml
text_gpu_device_index: 1
```

Left unset, text shares the lowest card with image generation. On a single-card host it is always shared,
so choose a text model and an image model list that fit side by side.

The compute path follows the backend your install was set up for: an NVIDIA install runs text on CUDA, an
AMD install on Vulkan, a CPU install on the CPU. Override it when text should differ from the install, for
example a text-only worker installed with the CPU build whose card should still serve text:

```yaml
text_backend_accelerator: cuda   # auto, cuda, vulkan or cpu
```

Two limits to know. koboldcpp's CUDA flag accepts cards 0 to 3 only. On Vulkan the card number is
koboldcpp's own numbering, which can differ from the worker's on a multi-GPU host; if the wrong card is
used, try the other index. Vulkan and CPU launches have not been verified by the maintainers.

### More than one generation at a time

`text_threads` is how many generations the backend runs at once. The worker launches the backend able to
do so and holds that many jobs. Each generation gets slower as the number rises (two at once ran at about
half speed each in our measurement, for the same total), so raise it only after measuring on your model,
and leave it at 1 if unsure.

## Attach to a backend you already run

Any backend that speaks the KoboldAI HTTP API works, on any platform:

```yaml
scribe: true
scribe_name: "My Unique Scribe"
text_backend_managed: false
kai_url: "http://localhost:5001"
# text_backend_password: "only-if-your-backend-requires-one"
```

The worker advertises the model your backend reports; set `text_model_name` if the horde knows it by another
name. `text_model`, the card and compute-path settings, and `text_backend_port` are unused here. If the
backend refuses the password, the worker stops asking for jobs and says so, and picks up a corrected
password on the next config reload. Run your backend with koboldcpp's own horde worker off (no `--hordekey`),
or the two will both pop jobs.

## Verifying it worked

- The dashboard's Text panel shows the model, and the backend row reaches ready.
- The horde lists your scribe name as a text worker.
- To test without serving the public, put the worker into maintenance from the horde's site or API: the horde
  then routes only your own account's requests to it.

## Switching back

Set `scribe: false`. The flow stops popping and, on the next start, no backend is launched. `scribe` can be
turned on while the worker runs; changing `text_backend_managed` takes effect at the next start.
